# FlowTrack UI Component Library

## Status

Phase 2 establishes the official reusable Blade/CSS component contracts. Existing screens are **not** automatically migrated by this phase; Phase 3 will replace legacy markup in controlled feature batches. The new library can coexist safely with current pages.

## Architectural contract

- Static visual values come from `resources/css/foundation/tokens.css`.
- Component styles live only under `resources/css/components/`.
- `resources/css/components.css` is composition-only.
- Official Blade components live under `resources/views/components/ui/`.
- New shared components use the `ft-` namespace.
- Official root styles are compatibility-anchored with `data-ft-ui-component` so legacy classes with the same name cannot be restyled accidentally.
- No official component stylesheet may introduce hard-coded colors or `!important`.
- No official Phase 2 Blade component may contain a `<style>` block or hard-coded color.
- Livewire/Alpine attributes pass through the component attribute bag wherever the component is interactive.
- Runtime Master Data colors use validated custom properties generated by `App\Support\MasterColor`; they are not static design tokens.

## Semantic variants

### Buttons

Allowed variants are `primary`, `secondary`, `tertiary`, and `danger`. Allowed sizes are `sm`, `md`, and `lg`. Use `loading` for the explicit loading state and `disabled` for unavailable actions.

```blade
<x-ui.button wire:click="save">Save</x-ui.button>
<x-ui.button variant="secondary" href="{{ route('jobs.index') }}">Cancel</x-ui.button>
<x-ui.button variant="danger" :loading="$deleting">Delete</x-ui.button>
<x-ui.icon-button label="Edit" wire:click="edit">✎</x-ui.icon-button>
```

### Badges

Prefer explicit variants for new code: `neutral`, `info`, `success`, `warning`, `danger`, or `purple`.

```blade
<x-ui.badge label="In Progress" variant="info" dot />
<x-ui.status-badge :label="$status->name" :color="$status->color" dot />
```

The historical `x-ui.badge :label="..."` call without a variant remains compatible with the old `badge/b-*` classes so existing screens do not visually change before Phase 3.

## Forms

Form components centralize label, required/optional indication, helper text, disabled/read-only states, `aria-invalid`, and validation messaging. Extra attributes such as `wire:model`, `autocomplete`, `step`, `min`, and `max` pass to the underlying control.

```blade
<x-ui.input
    name="reference"
    label="Reference"
    wire:model.live="reference"
    help="Internal order reference."
    required
/>

<x-ui.select
    name="priority"
    label="Priority"
    wire:model.live="priority"
    :options="$priorityOptions"
/>
```

`x-ui.remote-select` deliberately remains an adapter over the proven `x-ui.remote-filter` implementation in Phase 2. Phase 4 will unify remote search/multi-select query contracts and bounded selector behavior across features.

## Tables

Use named `head` and optional `foot` slots; row markup belongs in the default slot.

```blade
<x-ui.table caption="Orders">
    <x-slot:head>
        <tr><th>Order</th><th>Status</th></tr>
    </x-slot:head>
    @foreach($orders as $order)
        <tr><td>{{ $order->number }}</td><td>{{ $order->status }}</td></tr>
    @endforeach
</x-ui.table>
```

The `data-ft-ui-component="table"` marker is important because the current Dashboard already owns four legacy `.ft-table` instances. The official CSS therefore cannot leak into those screens until Phase 3 migrates them.

## Tabs, modal and tooltip accessibility

- `x-ui.tabs` renders `role="tablist"`.
- `x-ui.tab` renders `role="tab"`, `aria-selected`, optional `aria-controls`, and tab focus state.
- `x-ui.modal` renders `role="dialog"`, `aria-modal="true"`, and an `aria-labelledby` title relationship. Workflow state remains caller-owned so Livewire/Alpine can control it without embedding business logic in the component.
- `x-ui.tooltip` exposes tooltip content through `aria-describedby` and is reachable by keyboard focus.

## Runtime Master Data colors

`App\Support\MasterColor::style()` now emits both the new `--ft-dynamic-*` contract and the historical `--ft-master-*` variables. This preserves existing screens while letting official badges consume:

- `--ft-dynamic-color`
- `--ft-dynamic-bg`
- `--ft-dynamic-border`
- `--ft-dynamic-text`

Only validated Master Data colors may enter this inline custom-property path.

## Developer reference page

In `local` and `testing` environments, authenticated developers can open:

```text
/_dev/ui-kit
```

The route does not exist in production. It demonstrates buttons, badges, runtime colors, form controls, tables, tabs, feedback states, tooltip, modal and pagination using only official components.

## Governance

Run:

```bash
npm run quality:phase2
```

The Phase 2 gate verifies required CSS/Blade contracts, exact component import ownership, zero static colors/`!important` in official component CSS, `ft-` namespacing, no embedded component style blocks, compatibility markers, no growth of direct page-level root component markup, and a local/testing-only UI reference route.

`quality/ui-component-baseline.json` freezes the pre-Phase-2 direct-root markup debt. Never re-baseline it to allow a page to bypass the component library.

## Migration rule for Phase 3

For each legacy page/component implementation:

1. select the official `x-ui` contract;
2. reproduce current behavior and appearance;
3. compare approved screenshots at desktop/tablet/mobile;
4. run feature tests and `npm run quality:phase2`;
5. delete the replaced selector/markup;
6. confirm legacy debt decreases.

## Phase 4 shared search and filter architecture

Phase 4 promotes `x-ui.search-select`, `x-ui.multi-select`, `x-ui.search-input`, `x-ui.filter-bar`, `x-ui.filter-chip`, `x-ui.filter-reset`, and `x-ui.date-range` as the official interaction contracts. Large catalogs use `FilterOptionService::searchPage()` and may never be preloaded simply to populate a dropdown. Selected values are resolved independently of the visible page, and an incomplete/no-match search never substitutes unrelated results.

The historical `remote-filter`, `remote-select`, `select-filter`, `date-range-filter`, and `list-search` components are compatibility adapters only. Ordinary feature pages must not introduce new usage. See `docs/shared-filters.md` and `docs/refactor/PHASE_4_IMPLEMENTATION.md`.
