# FlowTracker Order Details — Phase 3: low-noise Livewire realtime

**Source:** `FlowTracker_Order_Details_Performance_Implementation_Playbook(3).docx`, Phase 3, pages 9–11. Implemented against the supplied `Archive 2(20261103-044120).zip` snapshot on 2026-11-03.

**Status:** Source implementation complete; production rollout and browser/server benchmarks **not** verified. This is an application-facing change with a default-OFF realtime feature flag. Do not claim the proposed >=50% request reduction until measured against an identical baseline.

## Invariants and changes

- **No new migrations, SQL queries, Eloquent relationships, query loops, queue types, or business-rule changes.** Observer subject resolution uses only scalar attributes already available on the changed model. Unrecognized records use the original broad refresh path.
- The two **Order Details** links in the Orders list no longer contain `wire:navigate.hover`; they retain `href` and `wire:navigate` click/keyboard/history semantics. Other pages are untouched.
- New `FLOWTRACK_ORDER_TARGETED_EVENTS_ENABLED=false` flag in `config/flowtrack.php`. Off: the original generic notification and workspace refresh Livewire events continue to work. On: a mounted Order Details page routes known incoming order events only to the active Order and relevant *already loaded* sections.
- The user notification Reverb payload already had `job_id`. A workspace identifier was added (no DB call). Unread-count and notification-state events continue updating the badge; they do not refresh Order Details unless an actual notification identifies the currently opened Order.
- Workspace broadcasts now carry `workspace_id`, `order_id` where known, `reason`, and `event_id` (the existing version token). Within a database transaction, different/unknown order identities collapse to a null scope and retain the existing broad refresh. Existing 1-second broadcast coalescing and cache keys were not changed.
- Scoped workspace events use `Livewire.dispatchTo` to update only appropriate component aliases. A document event can update workflow, attachments, activity, summary; an Activity event for the current Order updates only Activity; a Task event updates workflow, activity, summary. Only already-loaded lazy sections receive updates. Unknown/missing subject scope falls back to `flowtrack-refresh`.
- Server Livewire listeners match the event's Order ID to the **already mounted** component; existing query scoping and permissions remain unchanged. Client-provided IDs are only refresh hints, never authorization or data selectors.
- `workspace-refresh.js` still checks the existing persisted `data_version` after events/reconnect. With a scoped event it performs a fresh comparison to detect additional writes hidden by the existing one-second broadcast gate. If the version has advanced beyond the event, it requests a conservative broad refresh. This reuses the existing unread-count endpoint; it does not create a new query or endpoint. Periodic and reconnect recovery remain as before.

## Browser acceptance (with the new flag enabled **locally**)

1. Keep your Phase 2 Redis setup as previously verified. Set `FLOWTRACK_ORDER_TARGETED_EVENTS_ENABLED=true` in your **local** `.env`, `php artisan config:clear`, and hard reload the browser.
2. On `/orders`, hover over the Order number and the View menu link. **Zero** Order Details prefetch GETs. Click and keyboard Enter must still open the same Order and preserve back navigation.
3. Open Order A, wait for lazy sections to load; with another user send a notification for Order B. The unread badge changes, and **zero** Order Details Livewire requests should be caused by the unrelated notification. Verify the same for read/unread state updates.
4. Send a notification for Order A. The shell and already-loaded sections update, with usual role/visibility checks. A section not yet loaded should remain dormant and load fresh data when scrolled into view.
5. Update Task, document, product and Order Activity on Order A through normal authorized workflows. Confirm affected summary/section data is fresh. The app's own `order-runtime-refreshed` and hold/shipping events must still work.
6. Update Order B; there should be no Order A refresh from a **scoped** event. If source is unknown/ambiguous, the legacy broad fallback remains correct and is expected to use more requests.
7. Test two changes within the existing one-second workspace gate, two workspaces, websocket disconnect/reconnect, and a changed data version. The UI must converge without missing an authorized update.
8. Repeat 5 cold + 5 warm runs per representative Order, record Network requests, backend baseline count/query time/CPU, p50/p95 and 4xx/5xx. Compare with the same actions with the flag OFF. The >=50% request reduction is a **proposed** target, not a guaranteed result.

### Rollback

Set `FLOWTRACK_ORDER_TARGETED_EVENTS_ENABLED=false`, `php artisan config:clear`, then hard reload. This immediately restores original broad notification/workspace routing. Replacing `wire:navigate` with `wire:navigate.hover` on the two Orders list links restores the old speculative prefetch if that is separately required. No rollback migration is necessary.

### Explicit limits

- Workspace events for models without an in-memory Order identity still use the original broad refresh to avoid stale UI; this is intentionally conservative. In particular, polymorphic Activity on a Task cannot be resolved without a database lookup, so no lookup was added.
- The coordinator and lazy children are still authorized on every render. Phase 3 does **not** address the separate 600+ query Workflow maintenance outliers; that remains Phase 4.
- This patch does not add server-side event persistence or a full event-history replay. Recovery uses the existing workspace version check and scheduled polling. Verify reconnect/permission scenarios before production rollout.
